5.1 Upload Method: Debugger / ICSP

This section is the debugger path: the sketch is written straight into flash over ICSP (In-Circuit Serial Programming). On the two Curiosity boards the debugger is already on the board and this is what the Upload button does, with nothing to wire. On a board of your own it means a PICkit 4 or SNAP and five wires.

From the Arduino IDE — all four boards

  1. Tools → Board → Arduino_dsPIC33CK, then your board
  2. Tools → Port, and pick the board's COM port
  3. Click Upload (Ctrl+U)

On the dsPIC33CK256MC005 Curiosity Nano and the dsPIC33CK256MP508 Curiosity board that is the whole procedure: the on-board debugger (nEDBG / PKOB) is on the same USB cable as the Serial Monitor, so no PICkit, no breadboard and no external wiring are involved.

If you are driving an external PICkit 4 or SNAP instead, use Sketch → Upload Using Programmer and select the programmer under Tools → Programmer. Wiring for that case is below.

No debugger at all? On the dsPIC33CK256MC005 you can burn the serial bootloader once and upload over the COM port from then on — §5.2, and Part 6 in full.

Hardware Setup — external PICkit 4 / SNAP only


    PICkit 4 Header        dsPIC33CK32MP102
    +----------+           +--------+
    | Pin 1 ●--+-----------+- MCLR  | (pin 1)
    | Pin 2 ---+-----------+- VDD   | (pin 13 or 20)
    | Pin 3 ---+-----------+- GND   | (pin 8)
    | Pin 4 ---+-----------+- PGD1  | (program data)
    | Pin 5 ---+-----------+- PGC1  | (program clock)
    +----------+           +--------+

    ● = Arrow/triangle marking on PICkit (Pin 1 indicator)
Which debug pair? The core sets the ICS config bit per board in cores/arduino/system_config.c: ICS = PGD1 on the dsPIC33CK32MP102 and dsPIC33CK256MC002, and ICS = PGD3 on the dsPIC33CK256MC005 and dsPIC33CK256MP508, because their on-board debuggers are wired to PGC3/PGD3. Wire the PICkit to the pair your board selects, and check the schematic for where those pins come out.

  1. Build the project: Production → Build Main Project (F11)
  2. Ensure build succeeds with no errors
  3. Click Production → Make and Program Device Main Project
  4. Or use the toolbar button: green down-arrow icon
  5. Wait for output:

5.2 Upload Method: Serial Bootloader (dsPIC33CK256MC005)

Uploads a sketch over the same COM port the Serial Monitor uses, with no debugger involved. This is what makes the platform usable on a dsPIC33CK board that has nothing but a UART, and it removes MPLAB X from the day-to-day loop.

This section is the short version - enough to burn the bootloader once and then upload. Part 6: Serial Bootloader is the full guide: three ways to burn it, the memory map, how the interrupt forwarding works, a longer troubleshooting table, recovery procedures, and what to do if you are putting this bootloader on your own board.
Supported on dsPIC33CK256MC005 only. The other three devices have no bootloader and no Bootloader menu; they upload through a debugger. Earlier releases (1.0.0-1.0.2) offered a "UART Bootloader" programmer entry that could not work - no bootloader firmware existed. If you tried it and nothing happened, that is why.

One-time setup

  1. Pick whichever programmer you have under Tools → Programmer - PICkit 5, PICkit 4, MPLAB SNAP, PKOB4 (Curiosity On-Board) or nEDBG (Curiosity Nano On-Board) all work - then Tools → Burn Bootloader. Do not pick Serial Bootloader (UART) here; it cannot install itself. This step needs MPLAB X, and it is the only time you will need it.
  2. Tools → Bootloader → Serial (UART, 115200).

After that, press Upload as usual. There is no button to hold and no reset to time: the host asks the running sketch to reset itself, so it behaves like uploading to an Arduino. Python is required (it ships with nothing to install - pyserial is not needed), and 115200 is the only rate the bootloader speaks, so there is no baud setting.

Programming with a debugger erases the bootloader. ipecmd erases the entire device, so any upload through nEDBG, PICkit or SNAP - including Sketch → Upload Using Programmer - wipes the bootloader and you must burn it again. Set Bootloader back to None when you go back to the debugger.
A sketch with no Serial.begin() blocks the next serial upload. Soft entry works by asking the running sketch to reset itself, and a sketch that never starts its UART has nothing listening. NanoBlink is the obvious example, and it is the first one most people try. On a Curiosity Nano the fix takes no hands: run Tools → Burn Bootloader, which erases the sketch and leaves the board waiting in the bootloader, then upload normally. On a board with no debugger, hold SW0 through a power cycle instead. To avoid it entirely, put Serial.begin(115200); in setup() - every 04.CuriosityNANO example except NanoBlink already does.

What an upload actually does

  1. The host asks the running sketch to reset itself (it sweeps the common baud rates, since the sketch is at whatever rate its own Serial.begin() chose).
  2. The bootloader answers in its ~300 ms window after reset and reports its own memory geometry - the host never assumes it.
  3. The application region is erased. The bootloader's own code and the configuration words are outside that region and are never touched.
  4. The sketch is written, then verified by asking the device to checksum what it stored.
  5. Only then is the image marked valid, and the device jumps to it.

Because the image is marked valid last, pulling the cable mid-transfer is not a brick: the board comes back up in the bootloader and waits. It is recoverable over serial alone.

When a serial upload fails

SymptomCause and fix
"could not enter the bootloader" Most often the bootloader was never burned, or a debugger upload erased it - burn it again. Otherwise the sketch cannot cooperate (see the next row), or the wrong port is selected.
Upload works for some sketches, not others Soft entry needs the sketch to be running its serial interrupt. A sketch that never calls Serial.begin() - NanoBlink, for one - or that sits with interrupts disabled, cannot be asked to reset. On a Curiosity Nano, run Tools → Burn Bootloader: it clears the sketch and leaves the board in the bootloader, and needs no hands on the hardware. On a board with no debugger, hold SW0 while you unplug and replug USB. (The Curiosity Nano has no reset button, so unplugging is the only power cycle there is.)
"the sketch places code at 0x000000, below the application base" The sketch was built for the debugger. Select Bootloader → Serial (UART, 115200) and rebuild - the sketch has to be compiled for the bootloader, not just uploaded to it.
Access denied opening the port Close the Serial Monitor. Only one program can hold the port.
Sketch no longer fits The bootloader reserves flash for itself and adds a 1608-byte interrupt-forwarding table to every sketch, so the limit is 246784 bytes instead of 262144. Both are shown in the size line after a compile.

5.3 Troubleshooting: Build Errors

Error: "XC-DSC compiler not found"

Cause: XC-DSC is not installed, or is installed outside C:\Program Files\Microchip\. It does not need to be on PATH — the platform locates it when a build runs.

Solution:

  1. Install XC-DSC v4.00 or newer from microchip.com/xc-dsc — v4.00 is the first release with the C++ compiler this core needs
  2. Verify by full path: "C:\Program Files\Microchip\xc-dsc\v4.00\bin\xc-dsc-gcc.exe" --version
  3. If it is installed somewhere else, set build.compiler.path in platform.local.txt (or the XCDSC_PATH environment variable) — editing PATH has no effect on Arduino builds
  4. Restart Arduino IDE

Error: "Cannot find include file <xc.h>"

Cause: Device Family Pack (DFP) not installed.

Solution:

  1. In the Arduino IDE this should not happen: Boards Manager installs both Device Family Packs with the platform. If it does, remove the platform and reinstall it — a half-finished download is the usual cause.
  2. In MPLAB X: Tools → Packs, search dsPIC33CK-MP_DFP (or dsPIC33CK-MC_DFP for the dsPIC33CK256MC002 / dsPIC33CK256MC005), install, restart and rebuild.

Error: "Undefined symbol _PORTA" or "_TRISA"

Cause: Device not correctly set in project properties.

Solution:

  1. Right-click project → Properties
  2. Under "Conf: [default]" verify Device matches the part you are building for
  3. If changed, Clean and Rebuild

Error: "Multiple definition of '_main'" or "main already defined"

Cause: You have two main() functions (your own + the Arduino core's main.c).

Solution:

Remove any int main(void) from your sketch. Only write setup() and loop(). The Arduino core's main.c handles calling them.

Error: "Undefined symbol _setup" or "_loop"

Cause: Your sketch file doesn't define setup() and loop() functions.

Solution:

Ensure your sketch.c file contains both functions:

void setup() { /* ... */ }
void loop()  { /* ... */ }

Error: "Section .text will not fit in region 'program'"

Cause: the sketch is bigger than the flash on the part you selected. How much that is depends on the board — 32 KB on the dsPIC33CK32MP102, 256 KB on the other three. The Arduino IDE prints the figure it is measuring against after every Verify.

Solution:

  • Check you have the right board selected under Tools → Board before anything else — a 256 KB sketch aimed at the 32 KB part fails here
  • Remove unused code; the platform already links with -ffunction-sections -fdata-sections -Wl,--gc-sections, so unreferenced functions are dropped for you
  • Use smaller data types; double arithmetic and the float print paths are the usual surprises
  • In MPLAB X only: Properties → XC-DSC → Optimization → Level 1 or 2

Error: "'Serial' was not declared in this scope"

Cause: the sketch does not include the core header. Arduino.h already pulls in HardwareSerial.h, so one include is enough — adding HardwareSerial.h separately fixes nothing.

Solution:

Put this at the top of the sketch:

#include "Arduino.h"

5.4 Troubleshooting: Programming Errors

"Target device was not found" / "Failed to connect"

Solutions:

  • Check all 5 ICSP wires are securely connected
  • Verify PICkit Pin 1 (MCLR) alignment
  • Ensure VDD is 3.3V (not 5V)
  • Check that MCLR has a 10K pull-up resistor to VDD
  • Try: Project Properties → PICkit 4 → "Power target from PICkit 4" = checked

"Device ID does not match expected"

Solution:

The project device setting doesn't match the physical chip. Verify:

  • The selected board really is the part on your desk — Tools → Board in the Arduino IDE, or the project's Device in MPLAB X. The four boards this platform ships are easy to mix up.
  • Read the chip markings to confirm part number

"Programming failed - Device is code protected"

Solution:

  1. In MPLAB X IPE (standalone programmer tool)
  2. Select device and connect
  3. Click "Erase" → "Bulk Erase"
  4. This clears code protection
  5. Re-program your application

5.5 Troubleshooting: Runtime Issues

LED doesn't blink / Device seems dead after programming

Check these in order:

  1. Watchdog Timer: the core ships FWDTEN = ON_SW in cores/arduino/system_config.c — software-controlled, and left off at startup. If you enabled it yourself, a sketch that never clears it will reset in a loop.
  2. MCLR pin: Must be pulled HIGH (10K to VDD) for device to run
  3. Power supply: Measure VDD — must be 2.7-3.6V
  4. Oscillator: Check that config bits select correct clock source (FRC)
  5. Debug vs Release: Try "Release" build mode instead of "Debug"

millis() returns 0 / delay() doesn't work

Cause: Timer1 interrupt not firing.

Solution:

  • Verify init() is being called (it's in main.c — don't remove it)
  • Check Timer1 config: T1CONbits.TON = 1
  • Check interrupt enable: IEC0bits.T1IE = 1
  • Check interrupt flag clearing in ISR: IFS0bits.T1IF = 0
  • Verify PR1 calculation matches your FCY

analogRead() always returns 0 or 1023

Solutions:

  • Always 0: ADC may not be initialized. Check ADCON1Lbits.ADON = 1
  • Always 1023: Pin is floating (not connected). Verify wiring to pot/sensor
  • Ensure ANSEL bit is SET for the pin (analog mode). analogRead() does this automatically but verify
  • Check that TRIS bit is SET (input mode) for the analog pin

Serial output is garbled / random characters

Solutions:

  • Baud rate mismatch: Ensure terminal AND code use same baud (e.g., both 115200)
  • Clock mismatch: If F_CPU/FCY doesn't match reality, BRG calculation is wrong. Verify your actual clock: F_CPU=8000000 and FCY=4000000
  • Wrong PPS mapping: Serial.begin() maps the pins itself, from the variant's SERIAL_TX_RP_REG / SERIAL_RX_RP_NUM — RP58/RP59 (RC10/RC11) on the dsPIC33CK256MC005, RP37/RP36 (RB5/RB4) on the dsPIC33CK32MP102 and dsPIC33CK256MC002. If your own code writes those registers afterwards, it wins
  • 5V adapter: Use a 3.3V logic adapter. 5V TX into dsPIC can damage it

PWM (analogWrite) doesn't produce output

Solutions:

  • Only the SCCP pins support PWM: D5-D8 on every board, plus D58 on the dsPIC33CK256MP508. Every other pin falls through to a plain HIGH/LOW — see Part 3 §3.1
  • Check PPS output mapping — SCCP output must be routed to physical pin
  • Verify SCCP module is enabled: CCP1CON1Lbits.CCPON = 1
  • Measure with oscilloscope on the pin to verify PWM waveform

5.6 Debugging Tips

Using MPLAB X Debugger

  1. Set a breakpoint (click left margin of code line)
  2. Click Debug → Debug Main Project (Ctrl+F5)
  3. Program halts at breakpoint
  4. Use "Variables" window to inspect register values
  5. Step through code with F7 (step into) or F8 (step over)

Using Serial as Debug Output

// Add debug prints to narrow down issues
void setup()
{
    Serial.begin(115200);
    Serial.println("[DEBUG] setup() started");

    pinMode(LED_BUILTIN, OUTPUT);
    Serial.println("[DEBUG] pinMode done");

    // ... more init code ...
    Serial.println("[DEBUG] setup() complete");
}

void loop()
{
    Serial.println("[DEBUG] loop() top");
    // ... your code ...
}

Using LED as Debug Indicator

On the dsPIC33CK256MC005 the on-board LED is active LOW, so the pattern below runs inverted — still perfectly readable, but HIGH is the dark half.

// Quick blink patterns to indicate state
void debugBlink(int count) {
    int i;
    for (i = 0; i < count; i++) {
        digitalWrite(LED_BUILTIN, HIGH);
        delay(100);
        digitalWrite(LED_BUILTIN, LOW);
        delay(100);
    }
    delay(500);
}

// In your code:
debugBlink(1);  // 1 blink = reached point A
// ... code ...
debugBlink(2);  // 2 blinks = reached point B
// ... code ...
debugBlink(3);  // 3 blinks = reached point C

5.7 Frequently Asked Questions

Question Answer
Can I use Arduino libraries? C++ libraries work in principle (XC-DSC v4.00+ compiles this core as C++), but most still need porting: they assume AVR/ARM registers, or the String class, which this core does not provide.
Can I use 5V sensors? NO! dsPIC33CK is 3.3V only. Use a voltage divider or level shifter for 5V signals.
What's the max PWM frequency? Depends on FCY and prescaler. At FCY=4MHz with 8-bit: ~15.6 kHz. At FCY=50MHz: ~196 kHz.
Can I use multiple UARTs? All four devices have three UART modules (U1-U3, per the DFP's own device description). This core's Serial is UART1 only; U2 and U3 are reachable with raw registers plus your own PPS mapping.
How do I access dsPIC registers directly? Include <xc.h> and use register names directly: PORTA, LATB, T1CONbits.TON, etc.
Can I mix Arduino API and raw register access? Yes! You can use both in the same sketch. Just be careful not to conflict (e.g., don't reconfigure Timer1 — it's used by millis).
What if I need more flash/RAM? Switch to one of the bigger boards this platform already ships: the dsPIC33CK256MC005, dsPIC33CK256MC002 and dsPIC33CK256MP508 all have 256 KB of flash against the dsPIC33CK32MP102's 32 KB. Another dsPIC33CK part number is not a menu entry — it needs a variant and a boards.txt block adding, and its pin numbering will not match, because the pin map is per device (Part 3 §3.1).

One card per board, priority device first.
