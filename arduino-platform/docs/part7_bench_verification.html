Arduino_dsPIC33CK User Guide

Part 7: Verifying a Board at the Bench

Navigation: Part 1: Setup Part 2: Pin Mapping Part 3: API Reference Part 4: Testing Sketches Part 5: Upload & Troubleshooting Part 6: Serial Bootloader Part 7: Bench Verification
What this is. Part 6 tells you how to use the serial bootloader. This page tells you how to prove it works on a board in front of you, in eight steps, each with the output you should see and what it means when you do not see it. Work through it after a fresh install, after burning a bootloader onto a new board, or when something has started failing and you want to find out where.

Every step here is ordered so that it depends on as little as possible of the step after it. That is the whole value of a procedure over a checklist: when step 5 fails you already know steps 1 to 4 passed, so the fault is in a much smaller place. Resist the urge to skip ahead to the interesting part — the interesting part is where everyone's time gets lost.

7.1 Before you start

You needHow to check
A dsPIC33CK256MC005 Curiosity Nano (EV08P02A) The serial bootloader is supported on this device only. The other three boards in this platform compile but have no bootloader menu.
This platform, 1.0.4 or later Tools → Board → Boards Manager, search dspic33ck. In 1.0.3 the soft-entry sniffer was compiled into every board by mistake, so the size figures on this page will not match.
Python 3 on PATH python --version at a command prompt. Standard library only — there is nothing to pip install for the upload itself.
MPLAB X IPE, once Only to burn the bootloader in step 3. After that you never need it again.
pymcuprog, optional but recommended pip install pymcuprog. Used to reset the debugger's serial bridge, which ipecmd wedges every time it programs. Without it you unplug and replug instead.

Note the COM port your board appears on before you start — Windows Device Manager, or Tools → Port. It normally keeps the same number across reboots and reflashes.

7.2 1 Restart the Arduino IDE

Not optional, and easy to dismiss. The IDE reads platform.txt once, at startup. If you installed or upgraded this platform while the IDE was open, it is still running on the old copy.

The symptom is that Tools → Bootloader is missing altogether, or is present but its settings have no effect — which looks exactly like a broken package and sends you off investigating the wrong thing entirely.

7.3 2 Three settings, in this order

  • Tools → Board → Arduino_dsPIC33CK (dsPIC33CK256MC005 Curiosity Nano)
  • Tools → Programmer → nEDBG (Curiosity Nano On-Board)
  • Tools → Bootloader → Serial (UART, 115200)
Set Bootloader before you compile, not before you upload. It is not only an upload switch. It relinks your sketch to sit above the bootloader at 0x1800 and builds the interrupt-forwarding table into it. A sketch compiled under None cannot be uploaded over serial — and the reverse is also true, so remember to set it back when you return to the debugger.
Do not pick "Serial Bootloader (UART)" under Tools → Programmer. That is a different menu, listing debugger hardware. The serial path is driven entirely by Tools → Bootloader. Choosing it in the Programmer list is a common and confusing mistake.

7.4 3 Burn the bootloader

Tools → Burn Bootloader. It takes roughly fifteen seconds. You are looking for two lines:

Program Succeeded
...
Serial bridge ready.

The first is ipecmd. The second is the part that matters and is easy to overlook.

Program Succeeded without Serial bridge ready. means the COM port will deliver zero bytes. Programming with ipecmd wedges the Curiosity Nano's USB-CDC bridge every single time: the port still enumerates, still opens, and returns nothing, indefinitely. The upload script reboots the debugger afterwards to clear it, but only if pymcuprog is installed — otherwise it prints a note and carries on.

Fix: pymcuprog reboot-debugger, then wait about ten seconds for USB to re-enumerate. Or unplug and replug the board.

Never conclude anything about firmware from a silent port until after that reboot. During the original development of this bootloader, three separate firmwares — the Arduino core, a bare-metal UART test, and a bare-metal pin bit-bang that bypassed the UART entirely — were all "broken" for this reason and this reason alone.

Burning erases the chip, so the board is now sitting in the bootloader with no application. That is a useful state, and step 5 depends on it.

7.5 4 Compile first, and read two numbers

Open File → Examples → Arduino_dsPIC33CK → 04.CuriosityNANO → NanoSerialHello and press Verify (the tick), not Upload.

Compiling before uploading separates a build problem from an upload problem, and it gives you two numbers that confirm the Bootloader setting actually reached the compiler. Read them off the size line:

SettingNanoSerialHelloLimitWhat it tells you
Bootloader: None 4532 bytes 262144 The ordinary debugger build. Your sketch is charged nothing for a feature it is not using.
Bootloader: Serial 6272 bytes 246784 The limit drops by the bootloader's reserve, and the sketch grows by exactly 1740 bytes: 1608 of interrupt-forwarding table plus 132 of soft-entry sniffer.
The 1740 is the check, not the 6272. Your figure will differ the moment you change a line of the sketch, but the difference between the two settings is fixed by the design. If you switch to Serial and the sketch does not grow, the menu option is not reaching the compiler, and the upload in step 7 will fail with no useful diagnosis — it will simply report that no bootloader answered.

If you want the compiled image on disk — you will need it if you fall back to the manual commands in 7.10 — use Sketch → Export Compiled Binary. It writes next to your sketch:

build/microchip.dspic33ck.dspic33ck256mc005/NanoSerialHello.ino.hex
That folder name does not include the Bootloader setting. Both menu options export to the same path, and the filename gives you no hint which one produced it. If you have been switching settings, export again before trusting the file — uploading a None build over serial fails in a way that looks like a bootloader fault.

7.6 5 The first upload

Press Upload.

The board has no sketch on it right now, so it is already waiting in the bootloader. This step therefore tests the bootloader firmware and the host tool on their own, with the entry handshake taken out of the picture. You should see the host sync, erase the application area, write a run of rows, verify by CRC, commit, and jump.

The LED should then do whatever the sketch says, and the sketch is running.

7.7 6 Open the Serial Monitor

Tools → Serial Monitor, 115200 baud. You should see the uptime lines ticking.

You will probably not see the === dsPIC33CK256MC005 === banner, and that is not a fault. setup() runs the instant the bootloader jumps into your sketch, which is well before you can get the Serial Monitor open. The banner is printed into a port nobody is listening to. The ticking lines are the proof that it worked.

To see the banner, leave the monitor open and power-cycle the target only: 
pymcuprog setsupplyvoltage -l 0
pymcuprog setsupplyvoltage -l 3.3
This resets the MCU while leaving the USB bridge alive, so the port stays open across the reset. reboot-debugger cannot do this — it drops the port.
A silent monitor has a second, cheaper explanation: DTR. A terminal that does not assert DTR reads zero bytes from a perfectly healthy board, which is indistinguishable from the wedged bridge in step 3. The Arduino IDE's Serial Monitor and PuTTY assert DTR by default; hand-rolled readers using .NET System.IO.Ports or pyserial do not.

7.8 7 Upload a second time — the real test

Change something you can see — the delay, or the text it prints — and press Upload again, without touching the board.

This is the step the whole feature exists for. The board is now running your sketch, not the bootloader, so the host cannot simply talk to a waiting bootloader as it did in step 5. It has to ask the running sketch to reset itself: it sends a ten-byte magic sequence, the sketch's serial receive interrupt recognises it, sets a flag that survives a reset, and reboots into the bootloader.

If that works with no button held and no cable touched, the feature is doing what it claims. This is also the step that fails if the Bootloader setting was not applied at compile time, which is why step 4 checked the 1740 bytes.

A sketch that never calls Serial.begin() blocks the next serial upload. Soft entry needs a live serial receive interrupt in the running sketch. NanoBlink has no Serial in it at all — and it is the first example most people open. See 6.5; the way out is Tools → Burn Bootloader, which erases the sketch and leaves the board waiting, or holding SW0 through a power cycle.

7.9 8 Interrupt an upload on purpose

The last step checks the property you will care about most on the day you need it: that a failed upload leaves a board you can still recover, over serial, with no debugger.

  1. Press Upload.
  2. Unplug the USB cable part-way through the transfer, while rows are being written.
  3. Plug it back in and wait for the port to reappear.
  4. Press Upload again.

Two things must both be true. The board must still answer, and it must not have jumped into the half-written image. That is what writing the signature last buys: the image is marked valid only after every row has been verified by the device's own CRC-32, so an interrupted upload leaves no valid application and the board simply waits for the host again.

Use NanoSerialHello for this, not NanoBlink. The interrupted attempt leaves no valid application either way, so the retry does not need soft entry. But if the retry succeeds, the sketch it has just installed is the one that has to accept the upload after that — and NanoBlink never calls Serial.begin(), so it would lock the board out and turn a passing test into a recovery job.

7.10 When a step fails

Work from the smallest claim outwards. The host tool can be driven directly, which takes the IDE out of the picture entirely:

python "%LOCALAPPDATA%\Arduino15\packages\microchip\hardware\dspic33ck\<version>\tools\serial_upload.py" ^
  --port COM7 --hex path\to\sketch.ino.hex --verbose
Add thisTo find out
--dry-run Whether the HEX file itself is sane. Parses and checks it without opening a port, so it works with no board attached.
--no-soft-entry Whether the problem is the protocol or the entry handshake — the two independent halves. Run it right after Burn Bootloader, when the board is already waiting: if this succeeds and a normal upload does not, soft entry is your fault area, not the protocol.
--no-jump Leaves the board in the bootloader after committing, so you can upload repeatedly without soft entry being involved at all.
--verbose Reports retries. Occasional retries are normal; a wall of them points at the serial bridge rather than the protocol.

The three explanations worth ruling out first

SymptomLikely cause
No bootloader answered The running sketch has no Serial.begin(); or the sketch was compiled under Bootloader: None; or a previous debugger upload erased the bootloader. Run Burn Bootloader — it resolves all three.
Port opens but delivers nothing The CDC bridge is wedged from an ipecmd session, or your terminal does not assert DTR. Neither is a firmware fault. See 7.4 and 7.7.
Everything worked yesterday, nothing works today Check Tools → Bootloader is still Serial, and that nothing has been uploaded through Sketch → Upload Using Programmer since — that erases the whole device, bootloader included.

7.11 What this procedure does not prove

It is worth being precise about the edges, because a procedure that implies more coverage than it has is worse than a short one.

  • A power cut during a flash row write is not covered. Step 8 interrupts the transfer, and what the board decides when it reboots is genuinely verified. But the NVM controller being interrupted mid-write is a different event, and it has not been reproduced on a bench. It is a documented limit, not a tested one.
  • Nothing here covers the other three devices. The bootloader is dsPIC33CK256MC005 only. The other boards compile and upload through a debugger; they have no bootloader menu, and none of the size figures on this page apply to them.
  • It does not test your sketch. It tests that the board can be programmed. For the peripherals, work through Part 4 and the 04.CuriosityNANO examples.
  • Passing step 7 once does not prove every sketch can be replaced. Soft entry depends on the sketch that happens to be running. A sketch that disables interrupts for long periods, or never opens the serial port, needs Burn Bootloader or the SW0 route instead.
  • It does not prove a third-party USB-serial adapter works. Every upload in this procedure goes through the Curiosity Nano's own CDC bridge. Replacing that bridge with a CP2102 or FT232 should change nothing — the upload path contains no debugger at all — but it cannot be tried on this board, because the on-board debugger is already connected to the same two pins. See 6.9.
