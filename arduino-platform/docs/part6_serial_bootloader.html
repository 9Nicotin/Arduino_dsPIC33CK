Part 6: The Serial Bootloader

Navigation: Part 1: Setup Part 2: Pin Mapping Part 3: API Reference Part 4: Testing Sketches Part 5: Upload & Troubleshooting Part 6: Serial Bootloader Part 7: Bench Verification
In short: burn the bootloader once with a programmer, then set Tools → Bootloader → Serial (UART, 115200) and press Upload for the rest of the board's life. No debugger, no MPLAB X, no button to hold. If that is all you need, read 6.2 and 6.3 and stop.

6.1 What this is, and why it exists

Every other upload path in this platform goes through ipecmd, which lives inside MPLAB X. That has two consequences. MPLAB X becomes a hard prerequisite just to blink an LED, and a dsPIC33CK board that has nothing but a UART cannot be programmed from the Arduino IDE at all.

The serial bootloader is a small program that lives permanently in the first 6 KB of flash. It listens on the board's UART at reset, and if a host is talking to it, it erases and rewrites the rest of flash with whatever sketch it is sent. The Arduino IDE drives it over the same COM port the Serial Monitor uses.

The real target is not the Curiosity Nano. On the Curiosity boards the on-board debugger is faster and more capable, and it stays the default. The target is your own hardware — a dsPIC33CK on a board you designed, with a USB-serial bridge and no debugger on it. For that board this is the difference between "programmable from the Arduino IDE" and "not".

dsPIC33CK256MC005 only, for now. The other three supported devices have no bootloader and no Bootloader menu; they upload through a debugger exactly as before. Nothing about your existing sketches or workflow changes unless you opt in.

Releases 1.0.0–1.0.2 offered a programmer entry called "UART Bootloader" that could not possibly work, because no bootloader firmware existed yet. If you ever selected it and nothing happened, that is why.

What it costs

CostAmountNotes
Flash reserved for the bootloader 6 KB at the bottom, 2 KB at the top Never erased, never rewritten by an upload.
Flash added to your sketch 1740 bytes 1608 for the interrupt-forwarding table, plus 132 for the soft-entry sniffer — see 6.4. Both are added only when Bootloader is set to Serial; on None your sketch is not charged for either.
Sketch size limit 246784 instead of 262144 Both numbers appear in the size line after a compile.
Interrupt latency 2 instruction cycles 20 ns at 100 MHz. Every interrupt goes through one extra GOTO.
Upload speed 115200 baud, fixed A few seconds for a typical sketch. Not configurable — see 6.7.
Host requirement Python on PATH pyserial is not needed. The upload tool talks to the COM port through the Windows API directly, so there is nothing to pip install.

What it does not cost you is source compatibility. Your sketch keeps writing attachInterrupt(), Serial, tone() and hand-written ISRs like _T1Interrupt exactly as it does today. Nothing in a sketch or in the core needs to know a bootloader is present.

6.2 One-time setup: burning the bootloader

The bootloader itself cannot be installed over serial — a program cannot overwrite the flash it is running from, and the part that would have to be overwritten is precisely the part that must survive a power cut. Burning it needs a programmer, once. After that, the programmer can go back in the drawer.

Method A — from the Arduino IDE (easiest)

  1. Tools → Board → Arduino_dsPIC33CK (dsPIC33CK256MC005 Curiosity Nano)
  2. Tools → Programmer → whichever one you have plugged in:
    • PICkit 5
    • PICkit 4
    • MPLAB SNAP
    • PKOB4 (Curiosity On-Board)
    • nEDBG (Curiosity Nano On-Board)
    All five work. Do not pick Serial Bootloader (UART) here — you cannot burn a bootloader through the bootloader.
  3. Tools → Burn Bootloader

This erases the device and programs the bootloader plus the configuration words. It takes a few seconds. Expect output ending in:

Erase successful
program memory: start address = 0x0, end address = 0xfff
configuration memory
Program Succeeded
Operation Succeeded

Note the address range: 0x0 to 0xfff. Nothing above the application base is touched.

Burn Bootloader erases your sketch. That is expected — the board comes up in the bootloader with no application, LED0 blinking about twice a second to say "waiting". Upload a sketch and it stops blinking and runs.

Method B — from the command line

The IDE calls a wrapper script; you can call it yourself. It finds MPLAB X on its own, so no paths need configuring:

cd %LOCALAPPDATA%\Arduino15\packages\microchip\hardware\dspic33ck\1.0.3

tools\ipecmd-upload.bat PK4 33CK256MC005 ^
  "bootloaders\dspic33ck256mc005\bootloader-dspic33ck256mc005-115200-v1.hex"

The first argument is ipecmd's own tool code: PK4, PK5, SNAP, PKOB4 or nEDBG.

Method C — MPLAB IPE, or any other programmer software

The bootloader is an ordinary Intel HEX file. Load it into MPLAB IPE (or the tool of your choice), select device dsPIC33CK256MC005, and program. This is the route to use for a custom board, or for programming boards in batches.

Where the HEX file is

Shipped inside the platform package, so if you installed through Boards Manager you already have it:

%LOCALAPPDATA%\Arduino15\packages\microchip\hardware\dspic33ck\1.0.3\
    bootloaders\dspic33ck256mc005\
        bootloader-dspic33ck256mc005-115200-v1.hex

In the source repository it is at arduino-platform/microchip/dspic33ck/bootloaders/dspic33ck256mc005/, next to the C sources it was built from (bl_main.c, bl_uart.c, bl_nvm.c, bl_crc.c, bl_time.c). The -115200- in the name is the baud rate it is fixed at, and -v1 is the protocol version it speaks.

6.3 Everyday use: uploading a sketch

Settings

MenuSet to
Tools → Board Arduino_dsPIC33CK (dsPIC33CK256MC005 Curiosity Nano)
Tools → Port the board's COM port
Tools → Bootloader Serial (UART, 115200) — the one that matters

Then press Upload. That is the whole workflow. There is no button to hold, no reset to time, and no baud rate to choose.

Close the Serial Monitor before uploading. The upload tool needs exclusive use of the COM port; if the Monitor is holding it you get an access-denied error. Reopen it afterwards.
Read this one before your first upload: a sketch that never calls Serial.begin() blocks the next serial upload.

Soft entry works by asking the running sketch to reset itself, and the sketch can only hear that request if its serial receive interrupt is running. So if you upload a sketch with no Serial in it — NanoBlink is the obvious one, and it is the example most people try first — the upload succeeds, and then the next serial upload fails with "no bootloader answered". Nothing is broken, but you cannot get back in over serial alone.

Getting unstuck. On a Curiosity Nano, run Tools → Burn Bootloader: it erases the sketch and leaves the board in the bootloader, with no hands needed, and the next serial upload works. On a board with no debugger, hold SW0 through a power cycle instead.

Avoiding it. Put Serial.begin(115200); in setup() of any sketch you intend to keep iterating on over serial. It costs you nothing and it keeps the door open. Every 04.CuriosityNANO example except NanoBlink already does.

The Bootloader setting affects the build, not just the upload — the sketch is linked differently. So switching it means a recompile, and a sketch built for one setting cannot be uploaded with the other. The uploader detects that case and says so rather than corrupting the board.

What you should see

With File → Preferences → Show verbose output during: upload ticked:

serial_upload: not writing 4 config word(s) at 0x02BF18-0x02BF28: they belong to
               the bootloader and are the same in every sketch
serial_upload: looking for the bootloader on COM63
serial_upload: the sketch reset itself into the bootloader (magic accepted at 115200 baud)
serial_upload: board: DEVID 0x00A272 rev 0x000000, protocol 1, erase step 0x400
serial_upload: image 0x001800-0x0021A0, 1232 instruction words, CRC-32 0xB08BE980
serial_upload: erasing the application region
serial_upload: writing 10 block(s)
serial_upload:   1/10 blocks (10%)
   ...
serial_upload:   10/10 blocks (100%)
serial_upload: verifying with the board's own CRC-32
serial_upload: verified
serial_upload: 1232 instruction words written and verified on COM63
serial_upload: running the sketch

Without verbose output ticked you get the "written and verified" line only. That line is the confirmation the upload really happened — if you see nothing at all, the recipe never ran.

On a board that has no sketch yet, the third line reads "the bootloader is already listening" instead: there was nothing to ask to reset.

Going back to the debugger

Any upload through a debugger erases the bootloader. ipecmd erases the whole device, so Bootloader → None uploads, and Sketch → Upload Using Programmer, both wipe it. The board still works perfectly — it just has no bootloader any more, and serial uploads will stop working until you Burn Bootloader again.

This is not a bug that can be fixed. The bootloader lives at address 0, which is exactly what a whole-device erase clears first.

6.4 How it works inside

You do not need this section to use the bootloader. It is here because the design has consequences you can see — the 1740 bytes, the 2-cycle latency, the fact that a power cut mid-upload is survivable — and because anyone porting this to another dsPIC33CK will need to know why it is shaped this way.

The memory map

0x000000  reset vector      GOTO bootloader              ] bootloader-owned.
0x000004  interrupt table   200 slots, constants         ] Programmed ONCE when
0x000200  bootloader code   up to 0x1600                 ] you burn it, then
                                                         ] NEVER erased again.
--------------------------------------------- page boundary
0x001800  entry + forwarding table (1608 bytes)          ] application region.
0x001B24  your sketch                                    ] Erased and rewritten
0x02B700  signature: length / CRC-32 / magic             ] by every upload.
---------------------------------------------
0x02B800  unused, 2 KB                                    ] shares an erase page
0x02BF00  configuration words                             ] with config: never
                                                          ] touched.

The two "never" regions are the whole safety argument. Nothing an upload does can destroy the reset vector, the interrupt table, the bootloader, or the configuration words. There is no sequence of events — including yanking the cable at the worst possible moment — in which the board stops being able to accept a new upload over serial.

The 2 KB gap below the configuration words is not waste. The configuration words sit inside an erase page that starts at 0x2B800, and erasing that page would clear FWDTEN — and an erased FWDTEN reads as watchdog enabled, which would put the board into a reset loop. So the application stops short of that page.

Why your sketch grows by 1740 bytes

On this device the interrupt vector table is at a fixed address, 0x004, and cannot be moved. It also shares an erase page with the reset vector and the start of the bootloader. So if the application owned the vector table, every upload would have to erase the page containing the bootloader's own reset vector — and a power cut during that erase would leave a brick that only a programmer could fix.

Instead, each of the 200 vector slots is programmed once, at burn time, with a constant address pointing into a table of GOTO instructions at 0x1800. Your sketch rebuilds that table on every upload. An interrupt therefore goes hardware vector → GOTO → your handler, which costs 2 instruction cycles and 1608 bytes of flash.

The remaining 132 bytes of the 1740 are the soft-entry sniffer: a small state machine in the serial receive interrupt that watches for the host's 10-byte magic sequence and resets the board when it arrives. That is what lets an upload start without you touching the board, and it is why a sketch that never calls Serial.begin() cannot be replaced over serial — see 6.5.

Both costs are opt-in. They are compiled only when Bootloader is set to Serial, and a sketch built with None is byte-for-byte what it would have been without this feature existing. This was not true in release 1.0.3, where the sniffer compiled into every build on every board; 1.0.4 fixed it, and that is the only difference between those two releases.

The payoff is that no source code has to change. The alternative designs all break compatibility: the device's alternate vector table requires renaming every interrupt handler in the core and in your sketches (_T1Interrupt becomes _AltT1Interrupt), and the dual-partition feature does not exist on this device at all. Two instruction cycles is a good price for an unmodified API.

Getting into the bootloader — three ways

PathWhen it is used
Soft entry — the host asks the running sketch to reset itself Normal uploads. The host sends a 10-byte magic sequence; the serial receive interrupt in the core recognises it and triggers a software reset. This is why you never touch the board. The host sweeps the common baud rates, because the sketch is listening at whatever rate its own Serial.begin() chose.
The window at reset — ~300 ms of listening after every reset Always active. This is what catches the board when there is no valid sketch to run, and what the soft-entry reset lands in.
Hold SW0 through a power cycle The fallback when the sketch cannot cooperate — see the troubleshooting table. The bootloader stays put and waits indefinitely.

The upload sequence, and why an interrupted upload is safe

  1. The host gets the board into the bootloader.
  2. It asks the board to describe itself: protocol version, device ID, erase granularity, block size, and where the application region begins and ends. The host assumes no geometry — it asks. That is what makes the same tool usable on a future device.
  3. The application region is erased.
  4. The sketch is written in 128-word blocks. Every block is CRC-checked in transit, and the bootloader refuses any address outside the application region.
  5. The host asks the board to checksum what it actually stored, and compares.
  6. Only then is the signature row written — length, CRC-32 and a magic number.
  7. The board is told to jump. It re-validates the signature before branching.

Step 6 is the whole trick. The board only ever considers an application valid if the signature is present and its CRC-32 matches, and the signature is written last. Lose power during step 3, 4 or 5 and the signature is simply absent, so on the next reset the bootloader refuses to jump and waits for a host instead. Recovery is another serial upload, with no programmer involved.

6.5 Recovering a board

SituationWhat to do
Upload interrupted; board does nothing but blink LED0 Nothing is wrong — it is in the bootloader, waiting, exactly as designed. Upload again.
The sketch has no Serial.begin(), locks up, or disables interrupts for long stretches On a Curiosity Nano: Burn Bootloader. It erases the sketch and leaves the board in the bootloader, needs no hands, and is verified to restore serial uploads immediately.

On a board with no debugger: hold SW0, power-cycle, keep holding for a second, then upload. This is the designed fallback; it follows the same code path as the auto-jump decision that is verified, but the held-button case has not itself been reproduced on a bench, so treat it as expected-to-work rather than proven.
Serial uploads stopped working after you used the debugger The debugger erased the bootloader. Burn Bootloader again. The uploader detects this case and tells you so.
You want the board back to a plain, bootloader-free state Set Bootloader → None and upload with a programmer. That erases everything including the bootloader, which is what you asked for.
The bootloader cannot be bricked by anything the bootloader does. It owns the reset vector and never erases the page holding it. The only ways to remove it are a debugger or a programmer — which is the same thing as saying the only way to remove it is deliberately.

6.6 Troubleshooting

SymptomCause and fix
could not enter the bootloader on COMn In order of likelihood: the bootloader was never burned; a debugger upload erased it; the wrong port is selected; or the sketch cannot cooperate with soft entry (next row). Burn it again and retry.
Uploads work for some sketches but not others Soft entry needs the sketch to be servicing its serial receive interrupt. A sketch that never calls Serial.begin(), or that sits in a long section with interrupts disabled, cannot be asked to reset. Use the SW0 route above. This is a real limitation, not a misconfiguration.
the sketch places code at 0x000000, below the application base The sketch was compiled for the debugger. Select Bootloader → Serial (UART, 115200) and rebuild — it has to be compiled for the bootloader, not just uploaded to it. The uploader refuses rather than overwriting the bootloader with the sketch's own vector table.
Access denied / port busy Close the Serial Monitor. Only one program can hold a COM port.
Sketch no longer fits after switching to the bootloader Expected: the limit is 246784 rather than 262144, and the bootloader support code adds 1740 bytes. If you are that close to full, the debugger path gives you the space back.
Upload succeeds but the Serial Monitor shows nothing On Curiosity Nano boards this is usually the on-board debugger's USB-serial bridge being wedged by an earlier ipecmd run, not a problem with your sketch. Unplug and replug the board. See Part 5.
python not found Install Python and make sure it is on PATH. Nothing else is needed — do not install pyserial.
Upload reports success but the board runs the old sketch Should not happen — the image is verified by checksum before it is marked valid. If you see this, please report it with the verbose upload log.

6.7 Limits, stated plainly

LimitWhy
dsPIC33CK256MC005 only The linker scripts and the vector table are generated per device. The generator is device-portable, so adding a device is mechanical work rather than a redesign, but it has not been done or tested yet and nothing is claimed for the other three boards.
115200 baud, fixed The bootloader runs on the chip's reset-default 8 MHz internal oscillator with no PLL, which keeps it small and removes a whole class of start-up failure. At that clock 115200 is accurate to −0.7%; other rates are not reachable cleanly.
The bootloader cannot update itself Owning the reset vector is exactly what makes it impossible to erase — and therefore impossible to replace over serial. A new bootloader version needs a programmer. This is the correct trade.
Python required on the host The upload tool is a Python script using only the standard library. A self-contained executable is possible later if this proves to be a barrier.
Windows only As with the rest of the platform. The upload tool talks to the COM port through the Windows API.
Soft entry depends on a cooperating sketch See the troubleshooting table. On a board with no reset button this is genuinely awkward, and it is the main reason to put a reset button on your own hardware.
One case is reasoned about rather than measured. Interrupting a transfer and recovering from it is verified on hardware: the board refuses to jump into a half-written image and still answers the host. What has not been reproduced on a bench is a power cut landing inside a single flash row write, which is a window of about one millisecond. The design says the outcome is the same — the signature is still absent, so the image is still invalid — and the worst case either way is that you upload again. It is listed here because it is honest to distinguish what was tested from what was designed.

6.8 For your own hardware

If you are putting a dsPIC33CK256MC005 on your own board and want this to work, you need:

  • U1RX and U1TX brought out to a USB-serial bridge (CP2102, FT232, CH340, or another MCU). On the Curiosity Nano these are the pins the on-board debugger's CDC bridge uses.
  • An ICSP header — MCLR, VDD, GND, PGD, PGC. Needed once, to burn the bootloader. Five pads and a 0.1" header are enough.
  • A reset button, and ideally a button on the SW0 pin. Strongly recommended: it turns the one awkward recovery case into pressing a button.
  • Nothing else. No debugger, no crystal — the bootloader uses the internal oscillator.

The configuration words are programmed along with the bootloader, so a blank chip needs one ICSP session and nothing more.

6.9 Using a plain USB-serial adapter instead of the debugger

A common question: once the bootloader is burned, can a $2 USB-serial adapter replace the on-board debugger entirely?

Yes, and nothing in the platform has to change. The serial upload path never touches a debugger. It is one line in platform.txt and it runs serial_upload.py against a COM port — there is no ipecmd, no pymcuprog, and no mention of nEDBG anywhere in it. Whether that COM port belongs to the Curiosity Nano's built-in CDC bridge or to a CP2102 you soldered on makes no difference to the IDE, because by then it is just a COM port.

The wiring

Three wires. The bootloader's UART pins are fixed in the HEX that ships with this platform:

Adapter dsPIC33CK256MC005Note
TXD (adapter output)→ RC11 — U1RX, RP59, pin 32 Crossed: the adapter's transmit goes to the chip's receive.
RXD (adapter input)← RC10 — U1TX, RP58, pin 31 Remappable output 1 (U1TX) is assigned to RP58 by the bootloader itself.
GND—GND Required. Without a common ground the other two wires mean nothing.
VCCLeave it disconnected if the board is powered separately. Do not let two supplies fight.

115200 baud, 8N1. No flow control — the upload tool explicitly disables CTS/RTS handshaking and simply asserts DTR and RTS when it opens the port.

3.3 V logic only. The dsPIC33CK is a 3.3 V part and its pins are not 5 V tolerant here. A great many FTDI and CH340 cables sold as "TTL serial" drive 5 V, and one of those wired to RC11 can damage the input permanently. Check the adapter's jumper or buy the 3.3 V version. This is the one mistake on this page that costs a chip.

No reset wire is needed

Adapters are often wired DTR→reset on other platforms, through a capacitor, so the host can restart the target. That is not needed here: entry into the bootloader is in-band. The upload tool sends a magic byte sequence to the running sketch, the sketch's serial receive interrupt recognises it and resets the chip itself, and the bootloader then stays put. See 6.4 for the mechanism and the troubleshooting table for the case where it cannot work.

If you are designing your own board, a DTR-to-MCLR capacitor is still a nice thing to have. It is a convenience, not a requirement.

Wire a button to RD13 as well. The bootloader reads RD13 (SW0 on the Curiosity Nano, with its internal pull-up enabled) at power-up as a forced-entry path. Without it, a sketch that never calls Serial.begin() — or that sits with interrupts disabled — cannot be interrupted over serial at all, and the only way back is a programmer. That one button is what keeps a USB-serial adapter sufficient in every case.

The one thing a serial adapter cannot do

It cannot perform the initial burn. There is no ICSP over UART: putting the bootloader onto a blank chip needs MCLR, PGD and PGC, which means a programmer. So the honest rule is:

A programmer once per board. A serial adapter forever after.

Any of the five supported programmers can do that one burn — PICkit 4, PICkit 5, SNAP, PKoB4 or nEDBG all carry a Burn Bootloader recipe. The board's default is nEDBG only because that is what a Curiosity Nano has on it; select a different one under Tools → Programmer and Burn Bootloader works the same way. So "remove nEDBG" does not have to mean "own no programmer" — one PICkit on the bench is enough for an unlimited number of boards.

Different pins on your own board

RC10 and RC11 are compiled into the shipped bootloader HEX, not configured at run time. To move them, edit BL_TX_*, BL_RX_*, BL_TX_RP_REG and BL_RX_RP_NUM in bootloaders/dspic33ck256mc005/bl_config.h and rebuild with _build/build_bootloader.sh. The same file holds BL_LED and BL_SW0. Any remappable pin will do; the numbers are the RPn values from the device data sheet's pin-select tables, not the port letters.

This section is verified from the firmware and the tooling, not from a bench. The pin assignments, the baud rate, the absence of a debugger in the upload path and the programmer recipes are all read out of the shipped sources. What has not been done is an actual upload through a third-party adapter — and it cannot cleanly be tried on a Curiosity Nano, because the on-board debugger's CDC bridge is already connected to RC10 and RC11, so an external adapter on the same two pins would be contending with it. Proving this needs a board where those pins are free. Nothing about the design is expected to differ; it is listed as untested because it is untested.
