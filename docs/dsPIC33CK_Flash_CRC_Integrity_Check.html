1. Problem Statement

The situation:

  1. You compile a project in MPLAB X IDE → produces a .hex file
  2. You program the device using MPLAB IPE (via PICkit4, SNAP, or PKOB4)
  3. Programming reports "Verify OK" — MPLAB IPE says it passed
  4. You (or your customer) reads back the device with MPLAB IPE → produces a readback .hex file
  5. You compare the original .hex with the readback .hex → THEY DO NOT MATCH
  6. Customer computes CRC over the readback hex → CRC DOES NOT MATCH the CRC of the original hex
The Key Question: The device was programmed correctly (MPLAB IPE verified it). But when you read back and do a byte-by-byte comparison, certain addresses have different values. Why? Is the device corrupted?

Answer: NO, the device is NOT corrupted. The differences are expected hardware behavior. The device physically cannot store certain bytes the way the hex file specifies them. This is by design.

2. Root Cause Analysis — What Exactly Changes and Why

There are three main reasons why bytes differ between the original hex and the readback. All three are normal dsPIC33CK hardware behavior:

Reason 1: Phantom Bytes (Most Common — Affects EVERY Program Word)

dsPIC33CK has 24-bit instructions, but the Intel HEX format uses byte addresses. Each instruction occupies 4 byte positions in the hex file:

One Program Memory Word (at PC address 0x000200): Hex file byte layout: +--------+--------+--------+--------+ | Byte 0 | Byte 1 | Byte 2 | Byte 3 | | (inst | (inst | (inst | PHANTOM| | low) | mid) | high) | BYTE) | +--------+--------+--------+--------+ 0x04 0x02 0x00 0x00 or 0xFF <-- hex file may have 0xFF here What device stores and reads back: +--------+--------+--------+--------+ | Byte 0 | Byte 1 | Byte 2 | Byte 3 | | 0x04 | 0x02 | 0x00 | 0x00 | <-- ALWAYS 0x00 on readback +--------+--------+--------+--------+

Explanation: The dsPIC33CK only has 24-bit wide program memory. There is physically NO hardware to store the 4th byte (bits 24-31). When the linker generates the hex file, it may place 0x00 or 0xFF in this position. When you read back from the device, it always returns 0x00 because those bits don't exist in hardware.

Impact: Every single program word (every 4 bytes in the hex file) can have this mismatch at byte position 3. For a 256KB device, that's potentially thousands of mismatched bytes even though the device is programmed correctly.

Reason 2: Configuration Words (Unimplemented Bits)

Configuration registers (FOSCSEL, FOSC, FWDT, FPOR, FICD, etc.) have reserved and unimplemented bits. When you write to these registers:

  • Implemented bits: Store exactly what you wrote → read back matches
  • Unimplemented bits: Hardware ignores what you wrote → reads back as the default value (usually 1)
  • Reserved bits: May read back differently than written

Example — FWDT (Watchdog Timer Config):

Address 0x057F20 (FWDT register): Original hex file: 0xFF3F Device readback: 0x1F3F ^^ Bits 7:5 are unimplemented in FWDT. Hex has them as '1' (0xFF), device reads '0' (0x1F).

Why? The linker sets all unused bits to 1 (0xFF) for safety. But the hardware doesn't have those bits — they physically don't exist. On readback, only the implemented bits return their programmed values.

Reason 3: ECC (Error Correction Code) Parity Data

dsPIC33CK uses hardware ECC protection on program flash. For every group of program words, the device automatically generates and stores ECC parity bits in a separate flash region.

  • Your original hex file does NOT contain ECC data (the compiler doesn't generate it)
  • The device hardware auto-generates ECC during programming
  • If your readback tool reads the ECC region, those addresses will have data that was never in your hex file
Note: MPLAB IPE's normal readback typically excludes the ECC region. But if using a custom tool or reading "all memory," you'll see extra data.

Summary: Which Addresses Are Affected?

Cause Which Addresses How Many Bytes Predictable?
Phantom Bytes Every 4th byte in entire program memory 25% of all hex file bytes Yes — always 0x00 on readback
Config Words Last page of flash (device-specific address) 10-30 bytes (varies by register) Yes — per datasheet bit masks
ECC Parity Separate ECC flash region Not in original hex at all Yes — deterministic from program data

3. Real Example: Byte-by-Byte Comparison

Here is what you would actually see when comparing original hex vs. readback at specific addresses on a dsPIC33CK256MP508:

Example 1: Normal Program Memory (Phantom Byte Mismatch)

Address (hex file byte addr) Original Hex Readback Match? -------------------------------------------------------------- 0x000400 (instruction low) 04 04 YES 0x000401 (instruction mid) 02 02 YES 0x000402 (instruction high) 00 00 YES 0x000403 (phantom byte) FF 00 NO! 0x000404 (instruction low) 20 20 YES 0x000405 (instruction mid) 00 00 YES 0x000406 (instruction high) FA FA YES 0x000407 (phantom byte) FF 00 NO! 0x000408 (instruction low) 80 80 YES 0x000409 (instruction mid) 01 01 YES 0x00040A (instruction high) 78 78 YES 0x00040B (phantom byte) FF 00 NO!

Every 4th byte (0x03, 0x07, 0x0B, 0x0F...) will mismatch if the linker outputs 0xFF there.

Example 2: Configuration Word Area

Address Register Original Readback Why Different -------------------------------------------------------------- 0x055800 FSEC FF FF AB FF Unimplemented bits in FSEC read as 0 0x055808 FBSLIM FF FF FF FF (all bits implemented - matches!) 0x055818 FOSCSEL FF FF 67 00 Many bits unimplemented 0x05581C FOSC FF FF 63 00 Many bits unimplemented 0x055820 FWDT FF FF 1F 3F Watchdog config, sparse bits 0x055824 FPOR FF FF 07 00 Only 3 bits implemented 0x055828 FICD FF FF 03 00 Only ICD enable + reserved

Pattern: The linker writes 0xFFFF to all config words (meaning "all bits = 1, use defaults"). But only the implemented bits exist in hardware. Unimplemented bits read back as 0.

Example 3: Unused/Erased Flash

Address Original Readback Why Different -------------------------------------------------------------- 0x040000 FF FF FF FF (erased flash matches!) 0x040002 FF FF FF 00 Phantom byte: original=FF, readback=00 0x040004 FF FF FF FF (matches) 0x040006 FF FF FF 00 Phantom byte again

Even in erased (unused) flash, the phantom byte causes mismatch. Erased flash = 0xFFFFFF (24-bit), but readback shows 0x00FFFFFF (32-bit with phantom = 0x00).

4. Why Customer CRC Check Fails

The Customer's Process (What They Do)

CUSTOMER'S CURRENT PROCESS: =========================== Step 1: Receive .hex file from supplier (you) | v Step 2: Compute CRC over the .hex file contents CRC_original = CRC("firmware.hex") = 0x1234 | v Step 3: Program the device with firmware.hex | v Step 4: Read back the device memory | v Step 5: Compute CRC over the readback data CRC_readback = CRC("readback.hex") = 0x5678 <-- DIFFERENT! | v Step 6: Compare: 0x1234 != 0x5678 | v RESULT: CRC MISMATCH! FAIL! (but device is actually programmed correctly)

Why This Can Never Work

The CRC will NEVER match using this method because:

  1. The original hex file contains phantom bytes (0xFF or 0x00 depending on linker) + all config word bits set to the linker's defaults
  2. The device readback contains phantom bytes = 0x00 (always) + only implemented config bits
  3. These are physically different byte sequences, so their CRCs will always be different
  4. This is NOT a programming error — it's a fundamental property of the hardware
The core problem: The customer is comparing "what the linker intended" vs. "what the hardware can actually store." These will never be identical because the hardware has physical limitations (no phantom byte storage, unimplemented config bits).

Analogy: It's like writing "255.5" on a piece of paper and storing it in an 8-bit unsigned integer (max 255). When you read back "255", it's not corruption — the storage medium physically cannot hold 255.5.

How Many Bytes Differ? (Quantified)

Device Flash Size Total Bytes in Hex Phantom Byte Mismatches Config Mismatches
dsPIC33CK32MP102 32 KB ~44,000 ~11,000 ~20
dsPIC33CK256MP508 256 KB ~350,000 ~87,500 ~20
dsPIC33CK512MP308 512 KB ~720,000 ~180,000 ~20

Up to 25% of all bytes will mismatch due to phantom bytes alone! The CRC has zero chance of matching.

5. Solution: Compute CRC From What The Device Actually Stores

The Fundamental Insight

Instead of comparing "hex file CRC" vs. "readback CRC", we compute the CRC inside the device itself, from the actual flash content. This CRC will always be consistent because it reads what is physically stored.

How This Solves The Problem

THE CORRECT PROCESS: ==================== PROGRAMMING PHASE (factory/production): ---------------------------------------- Step 1: MPLAB X IDE builds firmware.hex (includes CRC module code) | v Step 2: Program device via IPE | v Step 3: Device boots for the first time | v Step 4: Firmware uses HARDWARE CRC MODULE to read its OWN flash (reads actual stored values: correct phantom bytes, correct config bits) | v Step 5: CRC result = 0xABCD (computed from actual flash content) | v Step 6: Firmware stores 0xABCD at a reserved flash address | v DONE. The "golden CRC" is now embedded in the device. VERIFICATION PHASE (customer/field): ------------------------------------ Step 1: Device powers on | v Step 2: Firmware reads flash again using CRC module (reads the SAME actual content as during programming) | v Step 3: CRC result = 0xABCD (same flash = same CRC, ALWAYS) | v Step 4: Compare with stored value: 0xABCD == 0xABCD | v RESULT: CRC MATCH! PASS! WHY IT ALWAYS WORKS: -------------------- - The CRC is computed from what is ACTUALLY in flash - Phantom bytes are always 0x00 when read by TBLRD → consistent - Config bits are their actual stored values → consistent - Same data in = same CRC out, EVERY TIME - No comparison with the original .hex file needed at all

Why This Is Better Than Comparing Hex Files

Approach Compare .hex files Hardware CRC (this solution)
What is compared Linker output vs. device readback Device flash vs. itself (stored reference)

6. How The Solution Works (Step by Step)

6.1 The CRC Module in dsPIC33CK

dsPIC33CK has a built-in hardware CRC engine. It is a programmable polynomial shift register that computes CRC at hardware speed. You feed data into it, and it outputs the CRC result.

CRC Module Block Diagram: ========================= Program Flash Memory (your firmware code) | | __builtin_tblrdl() / __builtin_tblrdh() | (CPU reads flash word-by-word) v +------------------+ | CRCDATL / CRCDATH| <-- Data Input FIFO (you write here) +------------------+ | | Hardware shifts data through polynomial v +------------------+ | CRC Shift Engine | <-- Configured with CRCXORL/H (polynomial) | (LFSR hardware) | +------------------+ | v +------------------+ | CRCWDATL/CRCWDATH| <-- Result (read CRC value here) +------------------+

6.2 Reading Flash Memory (TBLRD)

The dsPIC33CK can read its own program flash using Table Read instructions. In XC-DSC C code, you use compiler built-in functions:

// Set the page register to the upper bits of the address
TBLPAG = (uint16_t)(address >> 16);

// Read low 16 bits of the instruction word
uint16_t low_word = __builtin_tblrdl((uint16_t)(address & 0xFFFF));

// Read high 8 bits of the instruction word (+ phantom byte = 0x00)
uint16_t high_word = __builtin_tblrdh((uint16_t)(address & 0xFFFF));
Key Point: When firmware reads its own flash via TBLRD, it gets exactly what is physically stored. The phantom byte is always 0x00. Config bits return their actual values. This is the ground truth of what the device contains.

6.3 The Algorithm

// STEP 1: Enable the CRC hardware module
PMD3bits.CRCMD = 0;        // Enable clock to CRC module

// STEP 2: Configure CRC-16-CCITT polynomial (x^16 + x^12 + x^5 + 1)
CRCCON1 = 0x0000;          // Reset
CRCCON2bits.PLEN = 15;     // 16-bit polynomial
CRCCON2bits.DWIDTH = 15;   // 16-bit data input words
CRCXORL = 0x1021;          // Polynomial = 0x1021
CRCXORH = 0x0000;          // (upper bits unused for 16-bit CRC)

// STEP 3: Load seed (initial CRC value)
CRCWDATL = 0xFFFF;         // Standard seed for CRC-16-CCITT

// STEP 4: Enable and start
CRCCON1bits.CRCEN = 1;     // Enable module
CRCCON1bits.CRCGO = 1;     // Start CRC engine

// STEP 5: Feed every program word from flash into the CRC engine
for (address = START; address <= END; address += 2)
{
    TBLPAG = (uint16_t)(address >> 16);
    uint16_t offset = (uint16_t)(address & 0xFFFF);

    // Read instruction word from flash
    uint16_t low  = __builtin_tblrdl(offset);   // Bits 15:0
    uint16_t high = __builtin_tblrdh(offset);   // Bits 23:16 + phantom

    // Feed into CRC engine
    while (CRCCON1bits.CRCFUL);   // Wait if FIFO full
    CRCDATL = low;                // Feed low word

    while (CRCCON1bits.CRCFUL);   // Wait if FIFO full
    CRCDATL = high;               // Feed high word (includes phantom=0x00)
}

// STEP 6: Wait for engine to finish processing all data
while (!CRCCON1bits.CRCMPT);      // Wait until FIFO empty
Nop(); Nop();                     // Allow final shift to complete

// STEP 7: Stop and read result
CRCCON1bits.CRCGO = 0;
uint16_t crc_result = CRCWDATL;   // THIS IS THE CRC

// STEP 8: Compare with stored reference
uint16_t stored_crc = read_from_flash(CRC_STORAGE_ADDRESS);
if (crc_result == stored_crc) {
    // PASS - flash is intact
} else {
    // FAIL - flash is corrupted (real corruption!)
}

6.4 Storing the Reference CRC

On the very first boot after programming, the CRC storage location contains 0xFFFF (erased flash). The firmware detects this and automatically stores the computed CRC:

uint16_t stored_crc = read_from_flash(CRC_STORAGE_ADDRESS);

if (stored_crc == 0xFFFF) {
    // First boot - no reference CRC stored yet
    // Compute CRC and save it
    uint16_t crc = compute_crc_over_flash();
    write_to_flash(CRC_STORAGE_ADDRESS, crc);
    // Now the reference is embedded in the device
}
else {
    // Normal boot - verify integrity
    uint16_t crc = compute_crc_over_flash();
    if (crc != stored_crc) {
        // REAL corruption detected!
        halt_or_signal_error();
    }
}

6.5 What Address Range To CRC

Flash Memory Map: ================= 0x000000 +---------------------------+ | Reset Vector (GOTO main) | <-- Include in CRC 0x000004 +---------------------------+ | Interrupt Vector Table | <-- Include in CRC 0x000200 +---------------------------+ | | | PROGRAM MEMORY | <-- Include in CRC | (your firmware code) | | | +---------------------------+ | CRC STORAGE (1 page) | <-- EXCLUDE from CRC (this is where we store the result) +---------------------------+ | Configuration Words | <-- EXCLUDE from CRC (has unimplemented bits) +---------------------------+ CRC range: 0x000000 to (CRC_STORAGE_ADDRESS - 2) Exclude: CRC storage page + config words
Important: You MUST exclude the CRC storage address from the CRC computation. Otherwise you have a chicken-and-egg problem (the CRC depends on itself).

7. Production Flow For Customer

Scenario A: Device Self-Verifies (Recommended)

The simplest approach. No external tools needed. The device checks itself.

StepWhoActionResult
1 Supplier (you) Build firmware with CRC module included in the code firmware.hex includes CRC check in startup
2 Production line Program device with firmware.hex Device programmed, CRC storage = 0xFFFF (erased)
3 Production line Power-cycle the device (or just let it boot) First boot: firmware computes CRC, stores at reserved address
4 Customer (field) Device powers on normally Firmware computes CRC, compares with stored value, reports PASS/FAIL
Advantage: The customer does not need to compare hex files, use external CRC tools, or understand phantom bytes. The device simply reports "integrity OK" or "integrity FAIL" via a GPIO, LED, UART message, or register flag.

Scenario B: Customer Wants External Verification Number

If the customer insists on having a CRC number they can verify externally:

  1. Program the device (step 2 above)
  2. Let it boot once (step 3 — CRC gets stored)
  3. Read back the device with MPLAB IPE
  4. Read the CRC value from the known storage address (e.g., address 0x02AA00)
  5. This CRC value is the "golden reference"
  6. For every subsequent device programmed with the same firmware: read back, extract CRC from storage address, confirm it matches
Or even simpler: After first boot, read back the device. The CRC stored at the reserved address IS the verification number. Give this number to the customer as part of the release package: "firmware v2.1 = CRC 0xABCD at address 0x02AA00."

Scenario C: Customer Wants To Verify Without Booting The Device

If the customer needs to verify before the device runs (e.g., safety-critical, don't execute potentially corrupt code):

  1. After building firmware, program ONE "reference device"
  2. Let it boot (computes and stores CRC)
  3. Read back the CRC value
  4. Hard-code this value into your source code as a constant at the CRC storage address
  5. Rebuild the firmware (now the hex file contains the pre-computed CRC)
  6. Use this "final" hex for all production units
  7. Customer can read the CRC storage address from any programmed device and compare with the documented value — no boot required
// In your source code — hard-coded after first computation:
const uint16_t __attribute__((space(prog), address(0x02AA00)))
    FLASH_CRC_REFERENCE = 0xABCD;   // Computed from reference device
Caveat: Every time you change the firmware, you must re-compute the CRC (program a reference device, read back the value, update the constant, rebuild). This is a two-pass build process.

Summary: Which Scenario To Use?

ScenarioBest ForEffort
A: Self-verify at boot Most applications. Customer just checks pass/fail output. Low (include CRC code, done)
B: External number after boot Customer wants a "CRC certificate" per device Medium (read back after first boot)
C: Pre-computed in hex Safety-critical, verify before execution High (two-pass build)
Bottom Line: The original approach (CRC over raw hex file vs. CRC over readback) can NEVER work on dsPIC33CK due to phantom bytes and unimplemented config bits. The correct approach is to compute CRC from the device's actual flash content using the hardware CRC module. This gives a consistent, repeatable CRC that represents what the device truly stores.
